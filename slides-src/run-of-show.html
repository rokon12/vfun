What a virtual thread is

Nothing gets faster. Waiting gets cheap, so requests stop queueing for a thread.

  1. 05

    A platform thread is an OS thread 0:03

    Show what a waiting platform thread costs, so the room sees what virtual threads change.

    click 0“A platform thread is a thin wrapper around an operating-system thread. In the classic model one request takes one thread and keeps it until the response is written.”

    Point at one lane: the request on the left, its work drawn to the right.

    click 1“Now look at what the thread is doing. The solid part is real work. The hatched part is waiting for the database, and for a typical service that is most of the request. The thread is held the whole time, and it reserves about a megabyte of stack whether it works or waits.”

    Background. The megabyte is reserved address space, not all committed. The real cost is that OS threads are limited and expensive to switch, so every server caps them.

    click 2“Because threads are expensive we pool them. Tomcat’s default is 200. Request number 201 queues for a thread. Remember this pool. It comes back in the first demo, because it was quietly doing a second job.”

  2. 06

    A virtual thread belongs to the JVM 0:04

    Mount, park, unmount: the one mechanism the rest of the talk relies on.

    click 0“A virtual thread is a thread the JVM schedules itself. It needs an OS thread only while it is actually running. That OS thread is called its carrier, and by default there is one carrier per core.”

    click 1“When the virtual thread blocks, on a socket, a sleep or a lock, the JVM parks it: its stack is copied to the heap, and the carrier immediately picks up another virtual thread. Nobody holds an OS thread while waiting.”

    Background. The carriers are a ForkJoinPool. Its size is jdk.virtualThreadScheduler.parallelism, the number of processors by default.

    click 2“When the database answers, the virtual thread is runnable again and mounts on whichever carrier is free. It may be a different carrier every time. Your code doesn’t notice: it is still plain blocking code, top to bottom.”

    click 3“So a thousand requests can wait at once on four carriers. A parked virtual thread costs kilobytes of heap, so you stop pooling and create one new thread per request. This has been final since JDK 21.”

    Background. JEP 444. Never pool virtual threads: they are meant to be created per task and thrown away.

    The pool was your limit 0:16

    Explain why this never happened with platform threads.

    click 0“Why didn’t this happen before? With 200 platform threads, at most 200 requests could be inside the service. Nobody designed that as protection. It was an accident, but it was a limit.”

    click 1“With virtual threads every request gets in and parks on the pool. A parked thread costs almost nothing, so nothing pushes back, and the queue grows without bound.”

    click 2“That semaphore of eight is your HikariCP pool. In production these requests are parked inside getConnection(), and its default timeout is 30 seconds. So the symptom you actually see is a wall of connection-timeout exceptions half a minute later.”

    Background. The exception is SQLTransientConnectionException: “Connection is not available, request timed out after 30000ms”.

    click 3“The standard advice for virtual threads is: limit concurrency with a semaphore, not with a pool. We already have one. It limits how many run. It does not limit how many wait. Those are two different limits, and we only have the first.”

  6. 15

    The fix: say no at the door 0:19

    Add the missing limit: how many may be inside at all.

    click 0“The fix is six lines in handle().”

    Type them live in OverloadUnbounded.java if you like. OverloadBounded.java is the answer key.

    click 1“A second semaphore, called admission, with 32 permits. That is how many requests may be inside the service at all, running or waiting.”

    click 2“The important detail is tryAcquire, not acquire. If there is no permit we don’t wait at the door, we say no at once. Over HTTP that is a 503 with a Retry-After, and the caller still has time to do something useful.”

    click 3“And we always hand the permit back, in a finally.”

    click 4“Why 32? Eight are running, which leaves 24 waiting. At 80 ms a query the pool finishes about 100 a second, so 24 waiting is about 240 ms, plus the query itself: 330 ms, inside the 500 ms deadline. Pick the deadline first. The queue length follows from it.”

Questions you may get

Short answers. The demos already made the argument.

Should I pool virtual threads?
No. Pools are for expensive things. Limit the resource with a semaphore and leave the threads alone.
Is synchronized safe now?
For pinning, yes, from JDK 24. A thread still pins when it blocks inside native code or inside a class initializer. How long you hold the lock is still your job.
Does this happen with a real pool like HikariCP?
Yes. Requests park in getConnection() until connectionTimeout, which is 30 seconds by default.
How do I choose the admission limit?
Deadline first. Waiting time is roughly queue length times query time divided by connections. A bulkhead from Resilience4j does the same job.
How do I find a wide lock in production?
Take a thread dump with jcmd <pid> Thread.dump_to_file -format=json dump.json and look for many virtual threads stopped in the same method. Don’t promise JFR: it recorded no contention events for the wide lock in one test here.
What about CPU-bound work?
Virtual threads don’t help. There is no time slicing, and the carriers default to one per core. Keep a platform pool for CPU work.
Do ThreadLocals still work?
They work, but a cache per thread becomes a cache per request. Scoped values are final in JDK 25.
Is structured concurrency ready for production?
It is a preview in JDK 25 and needs --enable-preview. Until it is final, call cancel(true) in a finally.
